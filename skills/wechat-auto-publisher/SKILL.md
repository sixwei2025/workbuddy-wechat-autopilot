# 公众号自动化总控

开始时读 [统一交付标准](references/editorial-contract.md)。写教程/复盘类长文另读 [教程类文章范本](references/教程类文章范本.md)——十个可复用动作 + 自检表，样本是 2026-11-12 那篇 18 万流水复盘。**范本是质量标准，不是章节清单**，别照抄它的节数。教程/复盘类长文另读 [教程类爆款方法](references/教程类爆款方法.md) 与 [审稿判别附录](references/审稿判别附录.md) 第六节（AI 味可测清单）。这是本工作流唯一的编辑规范来源；最新用户要求优先。质量先于速度，不以 token 或时间目标跳过必要工作。

## 任务路由
- “写XX，发主号草稿箱”：完成整篇并上传袁六伟主号，不再逐项询问封面/排版。只是“写XX”而没有发布授权，不自行上传。
- “修改这篇”：读取现有成品，保留旧版，更新原 media_id；不新增重复草稿。
- “今日日报”：调用 aihot 核实当天资讯；调研任务不等于发布授权。
- 明确的其他账号要求必须匹配账号配置；不得用主号密钥顶替。缺失认证或目标身份不清时停止，不打印密钥。
- 默认不群发、不发布已上线文章。超时后先查询结果，禁止盲目重复 add。


## 🔴 结构不套模板（2026-11-12 袁总纠正，优先级最高）

**不许给文章套固定框架。**

原话：「谁告诉你每次写的文章都有一个什么固定的框架，必须包含 7 天路线的？」

犯的错：上一篇稿子里有一节「七天路线」，下一篇就默认也要有，甚至为了凑结构硬编一条出来。这不是方法，是模板惯性。

### 每篇的结构由内容自己决定

| 内容类型 | 天然结构 |
|---|---|
| 复盘 | 结果 → 为什么 → 怎么做的 → 踩了什么坑 |
| 观点 | 反常识 → 证据 → 边界 → 收束 |
| 教程 | 读者的问题 → 方法 → 步骤 → 验收标准 |
| 工具测评 | 结论 → 实测过程 → 对比 → 谁该用 |
| 清单 | 是什么 → 为什么入选 → 怎么开始 |

### 自检：写大纲时做一遍

1. 先列这篇要讲清哪几件事（不管分几节）
2. 列完再看：**有没有哪一节是上一篇带过来的、跟这篇内容无关**
3. 有就删。删完发现不够，说明这篇内容本来就少，不要注水

### 三种禁止

1. 上一篇有什么节，这一篇就有什么节
2. 用一套「标准 N 段结构」套所有文章
3. 为了凑结构加一节（没有七天可讲，硬编一个七天路线；没有案例可写，硬编一个「我有一个朋友」）

### 判断标准只有一条

**删掉这一节，读者会不会少拿到东西？**

会少，就留。不会少，就是凑数，删。


## 执行顺序
1. 按统一标准先做选题判断、标题候选、读者可带走的核心成果和整篇视觉规划，写入选题卡与配图清单；以争取2～5万阅读为目标，不承诺阅读量。明确选题和素材。用 yuanliuwei-writer 对齐个人文风；核对 Obsidian 真实观点及外部原始来源。不要假称朋友或实测。
2. 用 scripts/create_wechat_article_workspace.py 建 Obsidian 发布工作台。修改用原目录。只处理任务相关材料。
3. 写 public-safe 正文，按统一标准做开头、信息增量、实际可用性、故事、事实和手机段落审核。示例必须标明。
4. 配图：🔴 2026-11-12 起**不再使用小黑图 / AI 插画**，尽量全部用真实界面截图、真实成品图、真实后台记录。先收集与各节对应的原帖、官方页面、真实操作及结果截图；没有界面可截时只用少量数据卡/模板卡补位并标明整理示意。数量、证据边界和例外按统一交付标准执行。
5. 封面走 `wechat-cover-skill`（**2026-11-12 起换成六套主题，旧的「黑红金 v2b」废弃**）：先按内容结构选一套 —— `midnight` 午夜墨（数据复盘/搞钱）、`paper` 纸本墨（方法论/教程）、`kraft` 牛皮纸（个人经历/故事）、`indigo` 靛蓝瓷（AI工具/产品）、`swiss` 瑞士蓝（发布/清单/数据）、`brand` 汇芯红（通用，跟正文一致）。写 brief（`kicker` / `brand` / `title_lines` / `subtitle` / `author`）→ `scripts/render_cover_themes.py --brief <json> --themes <key> --out <dir>`，一次出横版 2350×1000 + 竖版 1080×1080，再缩 900×383 / 1:1 / 200px 三档。
   - 🔴 **真人照片绝不做黑白**（袁总原话「像我人已经去往西天了」），一律低饱和彩照，保留血色；要高级靠低饱和 + 纸感底 + 宋体 + 大留白，不靠抽颜色。
   - 🔴 **整个头必须完整在画面里**，只让身体底部出血，头顶留白 ≥40px。
   - 🔴 **封面上不写期号编号**（`NO.03 / 2026.11` 这类是实现细节，不是内容）。
   - 脚本自带硬闸：文字右边界 ≤1334（1:1 裁切线）、标题不压脸（face_box 按抠像裁后尺寸重映射）、贴边 warning。报错就改 brief 重渲，不许关闸。只改正文时不重做已可用封面。
6. 用 wechat-formatter 和 scripts/markdown_to_wechat_article.py 转换。图用 Markdown 图片或 [[img:文件名]] 指定位置；引用、任务说明合并轻块。依照用户2026-09-10要求，每篇正文最后默认插入 `assets/default-ending-poster.jpg`（本技能目录下固定原图），复制到文章assets后实际上传；用户明确取消或提供新图时按最新要求。其他未放置图片不能堆到文末。
   - **正文图 src 必须用 basename，不能带目录前缀**（2026-09-15 实际踩坑）：上传时兜底流程把正文图平铺 `scp` 到远端同一目录，远端校验器只按 `article_path.parent/src` 找图；src 写成 `assets/xx.png` → 远端找不到 → 校验 exit 2 → add 中止。本地文件仍可放 `assets/`，但 Markdown 图片引用与 `--content-image` 都要写 basename。
7. 上传前运行 scripts/validate_wechat_article.py --article article.local-images.json --max-paragraph 80（2–3 行短段落口径；2026-09-15 起由 180 下调为 80，`DEFAULT_MAX_PARAGRAPH` 已改为 80）。以完整意思组织段落，超 80 字提示过密；更长须记录具体理由。**上传入口同样显式传 --max-paragraph 80**，不依赖默认值。校验不能证明事实与审美，仍须人工复核。
   - 只有用户明确要求纯文字/特定长文等例外时，记录原要求，使用对应 --min-images、--max-paragraph、--no-require-xiaohei 参数；固定IP入口会传递给服务器校验，不用SKIP环境变量绕开整套检查。
8. 上传入口（2026-09-15 实测更新）：`skills/wechat-auto-publisher/scripts/publish_via_fixed_ip.py` 与 `find_draft_via_fixed_ip.py` 在**本机被沙箱/系统拦死**——两者都会 `Path('~/.ssh/...').is_file()`，报 `PermissionError: Operation not permitted`，**`dangerouslyDisableSandbox` 也绕不过**。必须走兜底：
   - 投递：`python3 ~/.workbuddy/scripts/publish_wechat_via_ssh.py --mode add|update --article <json> --thumb <封面> --content-image <图> --max-paragraph 80 --out <带回CDN的json>`（ssh/scp 二进制直连，二进制度密钥不受拦；**必须带 dangerouslyDisableSandbox**，ssh 需出网）。该脚本 `--max-paragraph` 自身默认是 65，**必须显式传 80**。
   - 查重：同理用 ssh 直连跑远端 `wechat_find_draft.py`（精确标题匹配），或用 `~/.workbuddy/skills/wechat-autopilot-main-account/scripts/wechat_find_draft.py` 的逻辑自行直连；不要因为脚本报权限错就跳过查重。
   - 配置优先 ~/.workbuddy/wechat_publish_server.json，现有默认服务器配置由脚本维护；不改网络或服务器配置。先查重，再 add/update；超时或失败先查询结果，禁止盲目重复 add。不要假定旧 work/secrets 路径存在。
9. 核对 ok、media_id 和上传后 CDN 图片，记录在05-草稿箱发布记录.md。出错说明具体阶段，不能说已完成。不要用真实上传测试 Skill 优化。

10. 用户要求发布后复盘时，按统一标准读取真实数据，填写06-发布复盘.md；缺数据标明未验证，不把草稿回执当阅读表现。

## 三层校验（2026-11-02 补第三层）

- **高级组件语法**：转换时支持 `:::` 容器，调用品牌红组件库，让关键判断一眼成卡。可用组件：引言卡 `:::quote`、数据卡 `:::stat`（格式 `数字 | 说明`）、标签卡 `:::tag`（`# 标签1 # 标签2` 或空格/逗号分隔）、结语卡 `:::end`、对比卡 `:::compare`（左栏/右栏用 `|` 分隔）、步骤卡 `:::step`（按 `1.` `2.` 编号自动切项）。组件定义、合规 HTML 与红点规范见 `references/组件库.md`。旧 Markdown 无 `:::` 时完全向后兼容。
- **样式关卡**：`scripts/validate_wechat_article.py` 的 forbidden-tags（div/class/id/style 标签属性误用、position/float/grid/var/@media/@import/外部字体/expression、**gradient**）与半角标点（中文后跟半角 `, ; ! ?`，代码块内豁免）。
- **乱码硬闸**：同一脚本新增 —— 双重转义 `&amp;quot;` / `&amp;#…`、文本节点残留反引号，命中即 exit 2。图说字号（12–13px）、居中、标红密度（3–6 处）走 `warnings` 软提示，默认不拦；加 `--strict-warnings` 可强制。
- **组件源头把关**：`scripts/component_lint.py` 扫描 `references/组件库.md` 里的 ```html 组件块，检查同样的反模式，退出码 0/1。组件库与产物校验构成闭环——改组件先过 lint，再进转换器。
- 用法示例：`:::stat 1-2元 | 单条聊天记录视频的 AI 成本 :::`、`:::compare 旧做法 | 整段染红 / 新做法 | 红只点在锚点 :::`。
